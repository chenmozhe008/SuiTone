## 二、已经确认的需求与边界

- 中文名称：随心调色。当前英文显示名：SuiTone；界面、菜单和应用包已改名。
- 图标暂用用户选定的候选板第二行中间，即第五款琥珀／青色光色环。此轮不重新做品牌。
- SwiftUI 原生 macOS 界面；算法复用 `engine/` 的 Python，不用 Swift 重写修图算法。
- 通用照片工具，适用于持续导入的不同照片。不能围绕单个湖水案例设计整个 App，也不能把案例水色写成全局默认值。
- 兼顾自然微调与明显的电影、胶片、复古等创作风格；明显风格应由用户选择。
- 照片是主角，中性灰、简洁、容易上手；功能强大不等于展示所有参数。
- 常规调整要快速出效果。暖缓存滑块预览目标小于一秒；不要把这个目标误写成大模型每次回答也必须小于一秒。
- 每步可回退，AI 实际做了什么要看得见。用户不希望每次普通调整都经历繁琐确认。
- 降噪／放大属于编辑阶段，要预览、比较、撤销，不能等导出时才决定。
- LUT 导出最后做，当前不应抢占主界面和开发优先级。
- 不自动加编号、装饰或文字。不要用“不裁切、不覆盖、支持哪些格式”等口号堆在界面底部。
- 用户后来修订了最初“不裁图、不覆盖”的绝对产品限制：裁切、文件替换应按专业工作流明确选择和处理冲突。**这不授权在开发测试中覆盖真实原图。**
- 调色浮点计算，输出前抖动量化，避免色阶断层；原图保留，不做破坏性测试。
- 使用 `/Users/forwardyan/.cache/photo-edit/venv/bin/python -B`。不装全局依赖，不修改已有模型，不清理案例或缓存目录。

## 三、当前实现是什么

### 3.1 界面与工作流

- 应用包：`dist/SuiTone.app`；旧的 `dist/PhotoEdit.app` 仍可能存在，查看时使用新包的完整路径。
- 目前右侧为“调色／修复／AI 对话”，默认仍以调色面板为主；**尚未改成 AI 优先的新结构**。
- 导入一张或文件夹后逐张保守初调，支持底部选片条、整批预览、当前／所选／整批作用范围。
- 16 款风格分“自然微调／创作风格”两组，每组 8 款；常用 4 款先显示，有照片缩略图和强度调整。
- 手动曝光、色温、饱和等已实现；“精细调整”里仍有节点、分区和人物参数，这是本轮受到质疑的现状。
- 参考匹配已实现：按可靠共同区域学习颜色和影调，结果成为可编辑参数。完整视觉验收尚未全部通过。
- 去杂物已形成“框选 → 生成预览 → 修复前后比较 → 保留／取消”的流程。保留后产生一次可撤销事务；目前没有完整画笔／点选体验。
- 画质已经移到编辑面板：降噪、原尺寸／2 倍／4 倍放大，逐张保存、按范围批量应用、可撤销。缓存画质结果后换调色参数不用重跑放大。
- JPEG／PNG 导出、保存和打开 `.photoedit` 记录已实现；导出沿用逐张画质。信息条仍在导出选项，编辑画布尚无其版式预览。

### 3.2 后端与已有模型

```text
SwiftUI
  → 常驻 loopback HTTP 服务（本次会话随机凭证）
  → Python 修图、分析、预览、缓存、原尺寸导出

对话输入
  → Python AssistantBridge
  → 已安装 Codex / Claude Code 的非交互进程
  → 结构化 JSON 调整计划
  → 校验目标 ID、参数范围和操作
  → Swift 应用参数、生成预览、记录撤销
```

- SegFormer：区域识别；LaMa：去杂物；Swin2SR：放大；已有模型在 `~/.cache/photo-edit/`。
- `match.py`、浮点调色、肤色保护、RAW、带缓存的预览及分条带原尺寸渲染均已有实现。
- 这些图像模型与“能聊天、理解照片含义的视觉语言模型”是不同能力。现在还没有内置聊天 VLM。

### 3.3 Codex／Claude Code 实际接法与限制

- 当前是 App 后台调用本机 CLI，不需要用户切到外部工具窗口操作。
- Codex 使用 `exec`、只读沙箱、临时会话、JSON Schema；Claude Code 使用 `-p`、JSON Schema，并关闭工具和 MCP、禁用 hooks 等。
- 每次请求新建进程；多轮上下文由 App 提供最近的文字消息和当前参数，不是完整的常驻 Agent 会话。
- 模型目前没有收到照片像素或参考图像；仅知道亮度、颜色与区域统计。因此不能可靠判断具体人物、构图、视觉风格或修复对象。
- 目前会返回调色参数和查看哪个选区；**对话尚未接入完整的修复、画质、参考图、撤销和导出工具调用**。不能把“界面有这个功能”等同于“AI 能操作这个功能”。
- 没有“看修改后的照片 → 评价 → 必要时修正”的效果复核流程。
- 检测到 CLI 文件只代表已安装，不等于账号、网络、额度和能力全都可用。已有错误分类和一次临时网络重试，但仍需完善状态反馈。

## 五、本轮审阅发现的具体问题

### 已确认

1. **产品主次没有体现用户定位。** 当前仍以风格和参数面板为主，AI 位于第三个页签；分区节点仍在精细调整中。
2. **AI 无视觉输入，也没有结果复核。** 当前有效的数值执行链与真正理解画面之间有明显缺口。
3. **对话与完整编辑能力没有打通。** 降噪／放大已有 UI，但不在对话可执行操作中；修复等同理。
4. **操作状态与对话记录脱节。** 撤销 AI 调整后，聊天卡片仍显示“已调整 1 张”和旧的数值变化，没有标记已撤销。见 `04-chat-after-undo.png`。
5. **通过结构测试不等于回复诚实。** Claude 的“无框选修复”用例没有返回修改，结构测试通过；但回复又说框选后告诉它即可直接处理，而当前对话根本没有修复执行接口。应按真实能力生成说明，而不是只靠系统提示。

### 从代码发现、尚未实机复现的疑点

- `WorkspaceAssistant.swift` 在请求发出时保存撤销前状态，接收结果时只检查 `assetID` 与调色参数，没有比较后来新增的 `quality`。若等待 AI 时用户改变画质，AI 事务的“之前状态”可能包含旧画质；撤销 AI 时可能连用户后改的画质一起退回。请构造并发场景验证，不能把推断写成已复现 Bug。
- 取消按钮在服务任务 ID 返回前可能无法生效；服务端取消与完成交界处、客户端应用结果前是否有完整保护，需要复核。已有“思考中立即取消”测试并未覆盖所有竞态。
- Codex 的只读沙箱限制写入，并不等于禁用所有读取工具；“只返回计划”当前还依赖提示约束。正式编辑助手应限制为明确的照片工具，不能把通用代码代理权限当作产品必需权限。
- 现有 `workflow_acceptance.py --ai` 会记录 AI 错误，但结尾仍可能给整体写 `engine_checks_passed`。本次新增 `ai_acceptance.py` 对任一用例失败会给 `incomplete_or_failed` 并返回非零。读取旧报告要分别看 AI 结果，不能只看整体字段。

这些疑点留给评审验证，本次未继续修改产品代码。

## 六、上一位 Agent 的建议方案（待讨论，未实施）

### 产品结构候选

1. 导入照片 → 温和自动调整 → 照片与 AI 对话为主界面。
2. AI 对话旁明确当前／所选／整批作用范围，给少量通用示例；无需先选区域节点或技术引擎。
3. “手动调整”提供常用风格、强度、明暗、冷暖、色彩，满足不聊天也能快速完成的需求。
4. 水／天空／土地／人物成为后台识别能力；局部操作由点选、圈选或自然语言触发，避免常驻一串语义栏目。用户是否仍需要可查的专业数值，待讨论。
5. 修复、降噪、放大等归入按需打开的工具，进入后提供与任务对应的直接操作；不要把所有工具同时铺满。
6. AI 普通调色直接更新可撤销的预览，并显示真实改动；比较、撤销、继续追调保持简单。复杂、慢或改变构图的操作采用合适的明确动作，不给所有操作统一套确认流程。

### 技术路线候选

```text
对话 + 当前照片／参考图 + 选区 + 当前编辑状态
  → 本机视觉语言模型，或用户选择的在线引擎
  → 受约束的编辑计划／工具调用
  → 同一套编辑事务与 Python 引擎
  → 预览 + 真实变更反馈 + 可撤销记录
  → 必要时有限次数的视觉效果复核
```

- 快捷风格和滑块继续直接调用本地引擎，不必为了每次轻微操作都启动大模型。
- 考虑本机 VLM 作为常用能力，Codex／Claude Code 作为可选联动。两者是否应分工、主次如何，需评测后决定。
- 所有入口共用编辑事务与能力清单；AI 回复以实际执行结果为依据，别让模型先宣布成功。
- 模型负责理解意图与画面；SegFormer 等继续负责现有区域分析；Python 继续负责像素处理，避免把通用 VLM 当作精确遮罩模型。
- 视觉编码、区域分析、增强结果与调色预览分别缓存，并明确源图／编辑版本，防止使用过期结果。控制模型常驻内存，兼顾修复和放大。
